# TP 스킬 저장소

이전가격(TP) 업무 스킬 13종의 **정본 저장소**. 여기가 원본이고, 배포본(`.plugin`)은 여기서 생성된다.

```
skills/                 정본 13종 (SKILL.md + references + scripts)
build_plugins.py        배포본 생성기
scripts/check_release.py 릴리스 검사 (CI가 실행)
scripts/update_manifest.py 매니페스트 갱신
docs/사용설명서.md       팀원용 사용 설명서
docs/배포안내문.md       설치 안내 (배포 파일과 함께 보내는 것)
.github/workflows/      CI
CODEOWNERS              변경 승인 규칙
```

> **스킬을 쓰기만 하는 팀원이라면** 이 README가 아니라 **[docs/사용설명서.md](docs/사용설명서.md)**를 보십시오.
> 설치 · 13종 용도 · 게이트 체인 순서 · 문제 대응이 정리되어 있습니다. 이 README는 정본을 **고치는 사람**을 위한 문서입니다.
>
> **배포하는 사람은** [docs/배포안내문.md](docs/배포안내문.md)를 배포 파일과 함께 보냅니다. 한 장짜리 설치 안내이며,
> 맨 앞 §0에 **그 판에서 실무가 달라지는 점**이 있습니다 — 팀원이 [등급 A]를 「스킬 고장」으로 오해하지 않게 하는 부분입니다.
>
> ⚠️ **두 문서는 배포본 docx와 같은 원고다.** 스킬을 고쳐 팀원의 실무가 달라지면 **여기와 docx를 함께 갱신**한다.
> v1.0.0 → v1.3.0 사이에 이 폴더만 방치되어 저장소 문서가 정본이 아니게 된 적이 있다.

---

## 왜 이 저장소가 필요한가

2026-08-06 작업분(tp-case-law v1.3~v1.5)이 **저장본에 반영되지 않은 채 유실**됐다. 세션 내부 사본만 고쳐졌고 아무도 알아채지 못했다. 닷새 뒤 발견했을 때는 v1.4가 막으려던 위험(가상 사건번호)이 그대로 살아 있었다.

이 저장소는 그 실패에 대한 답이다. **누가 무엇을 언제 바꿨는지 남기고, 바꿨는데 기록하지 않으면 병합되지 않게 한다.**

## 배포 흐름

```
skills/ 수정  →  매니페스트 갱신  →  PR  →  CI 통과  →  승인  →  main
                                                                  ↓
                                                       태그 v1.x  →  CI가 .plugin 생성
                                                                  ↓
                                                            팀원이 설치
```

### 스킬을 고칠 때

1. `skills/<스킬>/` 에서 내용을 고친다.
2. **매니페스트를 다시 산출한다.** 이걸 빠뜨리면 CI가 C1으로 막는다.
   ```bash
   python scripts/update_manifest.py <스킬>     # 생략하면 전체 13종
   ```
   ⚠️ 손으로 `find . | xargs sha256sum` 하지 말 것. `./SKILL.md` 형태가 되어
   경로 기준(`<스킬>/SKILL.md`)이 어긋난다. 실제로 이 안내문이 처음에 그렇게 적혀 있었고
   시험에서 걸렸다.
3. **개정 이력에 행을 추가한다.** 빠뜨리면 CI가 C2로 막는다.
4. 로컬 검사 후 PR을 올린다.
   ```bash
   python scripts/check_release.py
   ```

### 배포본을 만들 때

```bash
python build_plugins.py single    # tp-skills (13종)
python build_plugins.py split     # tp-common(3) / tp-outbound(5) / tp-inbound(5)
```

`dist/`는 `.gitignore` 대상이다. 배포본은 **태그를 붙였을 때 CI가 만든다** — main 병합만으로는 배포되지 않는다.

## CI 검사 항목

모두 **실제로 겪은 사고**에서 나왔다. 추상적인 린트가 아니다.

| 코드 | 검사 | 막으려는 사고 |
|---|---|---|
| **C1** | 각 스킬의 `MANIFEST.sha256`이 현재 파일과 일치 | 내용만 고치고 매니페스트를 안 고친 상태 |
| **C2** | SKILL.md가 바뀌었으면 개정 이력에 행 추가 | v1.6·v1.7이 이력 없이 지나가는 것 |
| **C3** | 「0000」·「00000」 형태 사건번호 없음 | `korea-cases.md`에 **11건**이 실재하지 않는 번호로 들어가 있던 사고 |
| **C4** | 이름이 소문자·숫자·하이픈 | 대문자·한글 이름은 플러그인 업로드에서 거부됨 |
| **C5** | `name`에 따옴표 없음(설치본 형태) | 설치 시 정규화되어 패키지와 해시가 어긋나는 것 |
| **C6** | Phase 0 무결성 확인 절 존재 | 자체검증이 빠진 스킬이 섞이는 것 |

## 설정해야 할 것 (GitHub 화면에서)

CI와 CODEOWNERS 파일만으로는 **강제되지 않는다.** 아래를 켜야 실제로 막힌다.

### 1. CODEOWNERS 계정 지정

`CODEOWNERS` 파일의 `@OWNER`를 실제 GitHub 계정으로 바꾼다.

### 2. 브랜치 보호 — Settings → Branches → Add rule (`main`)

| 항목 | 설정 |
|---|---|
| Require a pull request before merging | ✅ |
| └ Require approvals | ✅ **1명 이상** |
| └ Require review from Code Owners | ✅ **← 이걸 켜야 CODEOWNERS가 작동한다** |
| Require status checks to pass | ✅ → `verify` 선택 |
| └ Require branches to be up to date | ✅ |
| Do not allow bypassing the above settings | ✅ **관리자도 우회 못 하게** |

마지막 항목이 핵심이다. 켜지 않으면 관리자가 직접 push해서 전부 우회할 수 있고, 그러면 이 장치가 있으나 마나다.

### 3. 태그로 릴리스

```bash
git tag v1.0.0 && git push origin v1.0.0
```

CI가 `.plugin`과 동결 매니페스트를 만들어 Actions artifact로 올린다. 팀원에게는 그것을 배포한다.

## 3층 구조에서의 위치

배포보호 검토메모(2026-08-06)의 권고안이다.

| 층 | 무엇 | 상태 |
|---|---|---|
| **1층** 무결성 자체검증 | 각 스킬이 실행 전 스스로 정본 확인 (Phase 0) | **완료** (2026-08-11) |
| **2층** Git 통제 | 승인 없는 변경 차단 + CI 검사 + 태그 릴리스 | **이 저장소** |
| 3층 읽기 전용 속성 | 실수로 인한 수정만 방지 | 보조 수단 |

**1층은 드러나게 하고, 2층은 애초에 들어오지 못하게 한다.** 1층만으로는 「아무도 검증을 실행하지 않으면 검증되지 않는」 문제가 남고, 2층이 그걸 메운다.

## 알아 둘 제약

- **플러그인 이름**은 소문자·숫자·하이픈만. 대문자·한글 불가. description에는 한글 가능.
- **설치 시 frontmatter가 정규화**될 수 있다(`name`의 따옴표 제거). 해시는 **설치본 기준**으로 잡고 저장소 파일을 그 형태로 맞춰 둔다(C5가 검사).
- **플러그인 폴더명**(`plugin_XXXX`)은 설치할 때마다 다르다. 매니페스트에 절대경로를 쓰지 않는다.
- **개별 스킬과 플러그인은 동시에 존재할 수 있다.** 플러그인으로 전환한 뒤에는 개별 설치본을 삭제해야 한다. 남겨두면 내용이 다른 두 벌이 공존한다.
- **줄바꿈은 LF로 고정된다**(`.gitattributes`의 `eol=lf`). 무결성 검증은 바이트를 해시하므로, 작업트리가 CRLF가 되면 **전 파일이 「변조」로 오탐**된다. `git status`는 정규화 때문에 「변경 없음」으로 보여 원인을 찾기 어렵다. 편집기의 줄바꿈 설정을 LF로 바꾸지 말고 그대로 두면 된다. 이미 CRLF가 된 파일은 지운 뒤 `git checkout -- <파일>`로 되돌린다.
- **스킬은 다른 스킬을 공식적으로 참조할 수 없다.** 13종 중 10종이 `tp-case-law`를 조문 검증 수단으로 지목하지만 이는 산문 지시일 뿐이다. 3묶음으로 배포할 때 `tp-common`이 빠지면 그 지시는 조용히 실행되지 않는다 — 각 스킬 Phase 0가 `[미설치] tp-case-law`로 보고하게 해 두었다.
